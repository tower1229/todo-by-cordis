## 1. 目标与判断标准

最高目标：探索并验证基于 LLM 实现软件自迭代的最佳架构，尽可能简单、通用、可跨业务迁移。当前仓库是参考原型，Todo 是验证业务，不是通用内核的永久业务前提。

核心验证：同一个应用和同一批数据能真实生成、验证、运行、继续修改、修复和撤回新的实现；更换业务时，公共控制不应依赖 Todo 的字段、状态或页面。有效迭代、独立验收和可恢复性是约束，接口简洁与迁移成本是架构优化目标。性能和现有极简界面要求继续保留，但增加 Todo 功能、协议层数、测试数量或视觉工作不替代架构进步。

“最优雅”落实为：一次改动尽量集中在一个模块，调用者只学习很小的接口；为可替换性增加的抽象，应以实际第二种实现检验价值，不能靠命名证明通用。不给内部所有函数增加扩展钩子，不为尚不存在的适配器建包。

“性能最高”是优化目标，不能直接作为已实现结论。分别衡量任务命令 P95、候选生成/验证/切换时间、有效改进所消耗 token、连续迭代资源走势。模型耗时与本地执行分开；先建立基准，再优化占比最高的阶段。

## 3. 推荐架构

```mermaid
flowchart LR
  W[精美 Web 界面] --> H[Host：命令入口 / SQLite / 版本指针]
  H --> R[常驻子进程：Cordis 业务组合]
  R --> A[任务工作流插件]
  R --> B[字段与业务能力插件]
  H --> E[独立演化运行环境：受保护 AI loop]
  E --> C[候选源码 / 构建 / 验证]
  C --> H
```

这里“一个组合一个进程”指稳定运行时的业务组合，不禁止候选验证期间启动第二个临时组合。演化工作与业务运行不能挤在同一个故障域，否则待修复业务卡死会阻塞修复工作。两种环境复用同一运行器实现，不建立逐插件 RPC 系统。

仅保留四个深模块：

- **Workspace**：`query / command` 隐藏持久化、任务修订和数据提交。生成流程返回决策，Workspace 负责提交。
- **Runtime**：`start / invoke / close` 隐藏 Cordis 状态、跨进程通信、超时和退出。插件之间仍消费 Cordis 服务。
- **Evolution**：`command / observe / close` 隐藏模型调用、相关上下文、候选构建和验证；loop 为维护者持有的受保护策略，Agent 不能修改，记录由外部保存。
- **Release**：`activate / restore` 隐藏候选就绪、串行切换、活动指针和兼容状态映射。

这四个名字是模块设计，暂不创建四套包、服务或网络端点。M0 使用 JavaScript 小实验和 Node 内建测试器，减少工具链变量。正式 UI/API 再引入 TypeScript、React/Vite；依赖在需要时固定。

推荐子进程的依据：进程内直接调用最快，但生成代码同步死循环会阻塞监督器；Worker 可终止 JS，却与宿主共享进程故障范围。常驻子进程多一次 IPC，能重建整个 ESM 模块图。本机小载荷 P95 约 0.133ms，比 Worker 多约 0.040ms；目前值得用这点开销换取简单的组合重启机制。详见一手研究与基准，不外推为生产指标。

## 4. 简化发布规则

候选使用独立运行环境执行目标用例；失败直接丢弃候选运行环境，保留源码和原因。通过后串行处理活动切换：等待正在执行的任务命令完成，启动候选，检查当前数据是否兼容，在一个 SQLite 事务里更新必要状态映射和活动版本，切换运行引用，再关闭旧环境。

重启只读数据库中的活动版本：事务未提交继续旧版，已提交启动新版。新版尚未真正可运行时不能标记发布成功。M0 只证明精确手写组合下的机制；生产化仍需不可变源码产物、启动失败恢复和副作用约束。

首期新增字段采用增量数据，不用整库快照回退。流程回退如需 review→open，显式提供完整映射并保留复盘文本。UI 按动作/表单契约展示，取消补充输入不改变任务。

## 5. 自迭代质量与性能

先做最小差异：读当前实现与接口，生成候选，验证，切换，观察。每次请求只涉及一个主要能力，避免全站重新生成。只有出现第二个真实需求才增加新的通用契约。

保留小而有效的验证：新增行为正例、边界反例、旧有任务操作、数据保留。自动修复必须先让旧版本复现失败，再让新版本通过相同断言。模型新增测试可以补充证据，不能单凭它自写自测认定正确。

记录生成、构建、验证、切换各自耗时以及真实 usage。稳定上下文前缀、按需加载相关接口、复用常驻进程值得优化；是否使用缓存、并行模型调用或多 Agent 搜索，依据真实耗时和成功率决定，不先构建调度平台。

## 6. 视觉与体验方向（2026-09-07 更新）

用户调整为 **Microsoft To Do 的极简风格：干净、克制，任务优先**。覆盖之前暖白青绿和灵动助手的设计方向。使用最新版 Tailwind CSS 与 Base UI 减少自定义交互成本，具体约束见根目录 DESIGN.md。

日常界面只保留任务列表、筛选、搜索、添加与详情。AI 由常驻入口呼出需求侧栏，开始执行后进入专门进度视图；不是默认首页或永久一级导航。版本和日志等周边信息收进二级入口，保留生产运行时回归及旧数据库兼容。

Agent 只负责应用自迭代，不执行普通任务操作或通用问答。Plan 阶段读取真实实现、能力、依赖和测试，澄清必要业务取舍；计划包含目标、验收、步骤、数据影响及应用方式。用户点击开始后锁定需求，自动生成、验证和范围内修正；体验候选后再确认应用。执行中不能修改需求；必须改变范围时停止并保留证据，调整后重新规划。

执行过程展示实际服务端阶段；可以收起继续处理任务，回来恢复状态。禁止定时器伪造进度、无证据的成功状态和未接入时的模拟方案。M2 接通真实路由、模型生成、持久化运行和候选发布；前端只展示宿主记录的真实阶段。

## 8. 已知边界与后续决策

本节为 M1/M2 时点的历史背景，下面的模型选择与“尚未验证”不是 2026-10-23 的现状；当前证据及缺口见第 10 节。

M1 历史报告已覆盖浏览器与 1000 任务负载；真实模型、长期内存和大消息性能仍未验证。进程冷启动样本很少，不能把它当可靠尾延迟。Node 内建 SQLite 在实验中使用，正式存储驱动在 M1 结合运行环境固定。

M2 使用原生 Gemini Developer API、官方 @google/genai SDK 和 gemini-3.1-pro-preview。驱动只返回完整模型响应，Evolution 显式执行工具循环并保存历史；不使用自动工具执行、隐式重试或备用模型。密钥仅由服务端读取忽略的 .env 中 GEMINI_API_KEY。声明式插槽的表达范围用首个真实生成场景检验，避免为“任意 UI”提前设计语言。


## 9. M2 阶段约束与 Agent 重构修订（2026-09-07）

本节记录当时的目标约束，不表示每项模块解耦已经实现。历史固定预算不覆盖后来接受的用户追加授权；生产默认、冻结评测预算及跨运行的外部调用授权必须分别记录。

M2 的文本字段/动作是历史验收切片。新 Agent 使用行为目标、按需能力发现和完整候选产物，不以该切片限制生成范围。Runtime、Evolution、Release 不包含 Todo 字段或状态分支；不拆包。Gemini 驱动与工具执行、持久化、发布控制分离，不预建 Agent 框架。

计划冻结可执行目标、验收规则、稳定插件身份、基础版本和组合修订。点击开始前只调查和规划，开始后生成及验证，确认应用前不能改正式版本。候选使用现有工具链在独立环境构建和验证，源码、构建结果、契约版本和证据形成不可变产物。切换前重新核对组合和当前数据，事务提交活动版本、发布记录及回执，完成状态还须核对运行就绪。具体应用与恢复以新设计为准。

撤回使用已发布版本，不恢复数据库快照；期间新增的任务和字段保留。旧数据库增量加列，兼容旧工作流。单工作区一次运行，最多三个候选、十二次模型调用、十分钟活动执行；等待确认不计时。取消终止后续工具和发布，已经提交的结果仍显示完成。重启核对数据库中的提交事实，未完成运行标记中断，不自动重复调用模型。

本次不交付特定 Todo 功能，不重做无关 UI，不建设市场、模板生成器、多模型调度或远程部署。允许修改 Agent 所需的计划、进度及候选体验界面。Agent 自身策略纳入保护范围；本次工程重构由维护者实施，不赋予应用内 Agent 修改自身策略的能力。

### 10.1 复盘口径与结论

基线为本地 `37cb2a69a07ff9b5caf72ca54d368c22f95511c7`。盘点了该提交可达的 136 个提交、GitHub #1–#46、5 份 ADR、工程文档 00–06、M0/M1 报告、#8/#30/#35/#36/#46 的验收材料，以及 10 月的协议、职责对照、稳定性和交互验收归档；重点核对当前源码的模块接口、依赖、可写面及验证路径。没有重跑历史付费实验或修改其结果。

结论：四模块、单权威写入、故障可终止、冻结、独立验收、候选体验和绑定应用已经形成有价值的基础。复杂度主要累积在 Todo 语义编译、事实投影和复核协议之间，已影响职责局部性。主线没有被完全放弃，但研发重心有向“把固定 Todo 规格编译器做完整”偏移的风险。当前证明了多种 Todo 能力的迭代，尚未证明跨业务迁移，更不能称已经找到最佳架构。

这里区分三种判断：**实现事实**由源码和实际回归支持；**经验有效性**限定在已经暴露并验证过的失败模式；**架构建议**仍需下一业务和对照实验检验。保留保护门禁不等于保留它们当前的每一层实现，简化也不等于删除门禁。

### 10.6 后续主要关注什么

以下顺序按用户后续决定调整：先稳定现有业务，第二业务放到最后。架构建议不自动授权大范围重构；冻结、独立验收和应用确认继续保留。

1. **P0：以完整交付收益约束架构收缩。** 连续局部修复没有带来完整流程收益时，停止默认追加下一处提示或协议补丁，先梳理同一需求的调用链、单一权威、重复投影与审查职责，再选择一个能减少调用方知识的收缩方案做零付费对照。独立声明退出条件：必须保留原文、冻结、保护反例和应用确认，同时减少模型负担与维护位置；字符减少、纠错减少、测试增加均不能单独签发功能或效率通过。已有失败先复现并定位，正确性、恢复及证据丢失问题仍可修复。暂缓全面宿主生成、通用规格语言与大规模 Domain 重构，不为每类失败增加状态、配置或编排层。必填输入专项的历史局部收益保留，当前架构验证见 10.8。
2. **P0：守住目标正确性，统一复用评测。** 继续使用当前 stability-eval 的原文 oracle、正向/边界指标、实际职责绑定及归档；给旧专项脚本明确适用范围。不以正确阻塞抵消正向失败，不将计划自洽当原需求完整。保留未说明实体作用域导致合理追问的歧义证据，不能为减少追问而把验收假设伪装成用户要求。
3. **P1：验证现有业务连续交付与成本。** 同一业务的继续修改、继承、失败修正、预算续行、重启和保数据撤回共同组成退出条件；单场成功不替代连续链。保留原效率目标，追加后完成明确记为超初始目标；分别测资料、推理/输出和本地构建浏览器耗时。只向模型发送一份必要资料视图，保留复验需要的不可变快照。旧 #30 双轮标准另列，不以新专项冒名完成。
4. **后续：根据专项结果决定是否扩大架构比较。** 复用已有 host/model 对照，结合完整交付及上游失败判断；局部首候选改善不能证明全面接管更优。必要时才在相同能力、门禁、模型配置、预算和数据条件下比较较少专用协议的路径；生产不长期叠加并行执行机制。
5. **最后：用第二业务检验迁移。** 现有业务稳定性得到重复证据后，再选择真正不同的业务；例如库存记录、入库/预留/释放与非负约束，而非重命名 complete/reopen。记录业务适配量、核心改动和隐含规则，再依据真实阻碍收窄接口；不先建设通用实体平台，也不自动运行付费迁移实验。
