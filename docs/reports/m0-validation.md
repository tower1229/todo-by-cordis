## Cordis 的具体发现

1. `fiber.await()` 在缺依赖时能正常返回，state 仍为 PENDING。正式 Runtime 必须显式检查 ACTIVE。
2. provider 消失后消费者进入 PENDING，注册资源被撤销；新 provider 出现后消费者重新运行。
3. `dispose()` 等待异步清理，但 cleanup 抛错仅被记录，调用者不能以“不抛异常”证明清理成功。
4. 激活失败的 fiber 在 dispose 后 uid 已是 null，但 state 仍为 FAILED。状态显示需要区分运行失败与已脱离组合，不能强依赖终态枚举自动刷新。
5. 20 次循环中活动资源回到 0，已释放监听不再响应事件；这是本组登记资源证据，不是内存零增长声明。

## 运行方式基准

原始数据：[runtime-benchmark.json](runtime-benchmark.json)。每种方式 3 轮，每轮预热 300 次后测 3000 次，共 9000 次；同样的 Cordis provider/consumer 加法调用、小 JSON 输入、串行请求。包括适配层与消息往返，不包括 HTTP、数据库、模型和界面。

| 执行方式 | 往返 P50 | 往返 P95 | 冷启动中位数（仅 3 次） |
| --- | --- | --- | --- |
| 宿主直接调用 | 0.0075ms | 0.0106ms | 0.94ms |
| 单组合 Worker | 0.0296ms | 0.0928ms | 33.08ms |
| 单组合子进程 | 0.0532ms | 0.1331ms | 89.98ms |

结论：直接调用最低，Worker 次之；子进程 P95 多出的约 0.040ms 对本原型不是明显瓶颈。选常驻子进程是综合故障域与实现简单性的工程取舍，**没有声称子进程是最快方案**。默认按组合切换，不每次命令启动进程、不每插件一次 IPC。

冷启动未采用足够样本，JSON 中的 startup p95/p99 只是三个观测值的分位数，不作尾延迟承诺。串行微基准亦不证明并发吞吐、复杂插件成本或生产性能。
