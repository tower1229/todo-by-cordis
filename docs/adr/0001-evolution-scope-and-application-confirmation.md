# 自迭代覆盖业务实现，确认绑定可体验候选

2026-09-07，用户在设计访谈中确认 Q1、Q2 采用推荐方案。自迭代 Agent 专门负责应用改进，可修改插件、业务界面、运行能力和扩展接口；保留最小的验证、发布和恢复机制，不允许 Agent 自行修改。仅能修改现有插件的方案会将缺失接口变成永久能力上限；允许修改整个项目则失去独立验证与恢复依据。具体保护范围见 ADR 0002。

按 Q13 最终确认，先调查并展示计划，由用户点击开始执行；随后自动生成、验证和修正候选，用户体验具体结果后再确认应用。开始执行与应用确认分别控制开始工作和正式生效，范围内的候选修正不逐步询问。需要付费调用、外发数据等额外授权时，在发生前单独处理，已有授权继续有效。此决定取代 Q2 中生成前无需点击开始的安排，并覆盖 PRODUCT.md 和 docs/engineering/00-core-direction-v2.md 中与最终两阶段确认流程冲突的规则。详细交互见 ADR 0004；设计访谈记录不单独授权实施代码变更。

本次交付目标是重构自带 Agent，不是完成闹钟提醒功能。用户随后明确纠正了 Q3 的范围：提醒仅用于说明现有 Agent 的问题，不作为本次必须交付的业务功能。具体功能的行为细节由重构后的 Agent 在规划阶段自行与用户沟通确认，本次访谈不继续设计提醒渠道和停机规则。

用户在 Q9 确认按通用行为验收：需求澄清、读取真实实现、能力缺口规划、真实候选生成、失败后修正、确认后应用、同一能力继续修改，以及取消与恢复。使用不同类型的测试需求，至少一条超出原有文本字段契约；不预置业务答案，也不把任何特定功能列为本次产品交付。不能只凭提示词修改或方案输出认定完成。
